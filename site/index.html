Enloop — managing human attention

Fix the bottleneck in human‑in‑the‑loop.

The human is the slowest step in any AI feedback cycle. Enloop makes that step ruthlessly effective: your agent writes the test case, a Chrome side panel walks you through it, and whatever you say along the way goes straight back to the agent.

Mid-run

The screen moved on. The test catches up while you run it.

The page in front of you no longer matches the step? Ask from the step itself. Your question reaches the agent session watching the folder with a screenshot and the page's structure attached. It answers from the app's source — and when the step was the problem, a patched version of the test is waiting. One click loads it into the run you are in, and every result you already recorded stays.

  • Ask from the step

    Select the part that confuses you and type the question. Untick the screenshot or the page snapshot if you would rather not send them — both stay in your folder either way.

  • Watch it think

    The panel shows what the agent is doing in its own words — Reading the form, Found it: the button was restyled — so a long think never looks like a crash. Wrong question? Withdraw it.

  • Load the patch

    A mid-run patch is a minor version: v1 becomes v1.1. The panel checks that every step you finished is unchanged before it offers the swap, and keeps every recorded result.

The format

A test case is one Markdown file.

Committed next to the code it tests, diffable in a pull request, readable without any tool at all. An agent writes it; the side panel turns each line into something that does the work for you.

The principle

Any friction is a defect.

Whoever follows a case may never have seen the app, and is not going to learn it first. So everything was worked out when the case was written, and the person running it is never:

  1. asked to make a decision

    Which environment, which account, which record, whether a step applies. The case decided.

  2. asked to provide a value

    A URL, an id, something to type. Every value was resolved before the run began.

  3. asked to look anything up

    A route from a menu, a fixture from a seed file. If it can be looked up, it already was.

Features

Everything a run needs is already in the panel.

While you run

Kind: quick

One case, two depths

Steps marked as the core path make a two-minute Quick run. Full covers the edge cases, error states and cleanup. Written once, never duplicated.

feedback.md

Comments with an address

Tick who a comment is for and each audience gets its own section in the run's feedback file. The box saves as you type.

DeveloperProductTest writerDocsOps

console.md

The console, beside the step

Switch capture on and console errors and failed requests land in the report next to the step where they happened. Off by default; never headers, never bodies.

▶ Run

Setup commands, one click

A seed script named in the case gets a Run button. The agent session watching your folder runs it in the repo and streams the output into the panel. Stop kills it.

jumped over

Start further in

A run got dirty at step four? Start a fresh one and jump straight back to it. Jumped steps are recorded as jumped, never as steps you chose to skip.

run.json

Nothing lives only in the panel

Every mark, note and comment is written to the run's folder as it happens. Click into the page, close the panel, restart the browser — the run resumes where you were.

After the run

/enloop:check

A verdict per failure

Back in the repo, check reads the run and makes the call the tester cannot: was the app wrong, or the case? Each verdict comes with its evidence. Case defects it fixes itself, as the next version.

VerdictWhat it meansEvidence it must give
App bug Behaviour contradicts the app's own source file.ext:123 and the mechanism
Case defect The step was stale, wrong or unanswerable The grep showing the selector or route is gone
Environment Wrong build, missing fixture, bad integration state What must be true for a rerun to mean anything
Not reproducible Could not be located in source from here What it would take to reproduce
⚒ Prompt to fix this

A finding becomes a prompt

One click gathers a step's text, your comments, the questions you asked and what the console printed into a prompt for your coding agent. No agent on this machine? Copy the whole run's feedback into a ticket instead.

rules/<project>.md

It gets better at your app

A comment for the test writer that is really a standing rule is promoted to the project's rules file, read before every later case. Stars on well-written steps teach the shape worth repeating.

Selector:

Stale steps, caught early

Check sweeps every address and selector against current source — on steps that passed too. A selector that changed under a passing step is next run's mystery failure.

report.md

A report worth sharing

Every run freezes the exact case it executed and writes a readable report: each step, its verdict, what was said about it, and the address every domain resolved to.

Around the run

environments.json

Environments

Local, staging, prod, a preview that lives one afternoon. Pick one and every address in the case points there; each shows green or red, so a wrong tab is visible before you click. No environment ever holds a password.

Share with no install

Copy a link from the panel and the case opens as a checklist in any browser. The case travels inside the link, after the #, so it never reaches a server. Or hand over one self-contained HTML page.

A user guide nobody screenshots

Write the case for an end user and its run becomes the guide. The runner takes each photo at the right moment — cropped, numbered callouts, blur where needed — and exports Markdown or one HTML page.

data-testid

Selectors that exist

The skills never invent a selector. instrument adds the missing handles in the convention your repo already has, and checks they survive the production build.

test-cases/ · runs/

Your folder is the database

Cases, runs and reports are plain files in a folder you pick, read and written directly by the browser. Commit them next to the code they test.

Grant access

Asks for nothing up front

Installing requests no site permissions. The panel asks for one site, once, the first time a step needs to act on it.

The skills

Eight skills, for the agent you already use.

One plugin for Claude Code and Codex. The skills run from inside the repo of the app you are testing, read its source, and validate everything they write with the real parser before it lands.

  • setup Once per repo: the project name, the deployments cases run against, and the selector convention. /enloop:setup
  • quick The two-minute happy-path case for the branch you are on. /enloop:quick
  • full The whole article — edge cases, error states, cleanup — extending the quick case in place. /enloop:full
  • check Triages a finished run: a verdict per failure, and fixes for what the case got wrong. /enloop:check
  • serve Stays in the loop during a run: answers questions, patches the case, runs its commands. /enloop:serve
  • instrument Adds test handles to the app's source. Attribute-only, so the diff is reviewable. /enloop:instrument
  • guide Writes a case in end-user prose, with photo specs the runner takes. /enloop:guide
  • export-guide Turns a finished run into a Markdown folder or one HTML page. /enloop:export-guide

In Codex the same skills are $setup, $quick, $check and so on.
